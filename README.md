# 코리아둘레길 · 오륙도 안전걷기로드

부산치유협회의 체험 신청과 회차별 운영을 위한 첫 개발 버전입니다.
Next.js + Supabase, GitHub 저장 및 Vercel 배포를 기준으로 구성했습니다.

**현재 상태:** 사용자가 Vercel 배포, 관리자 로그인, 3단계 설치와 기존 신청자 가져오기를 완료했습니다. 이번 변경은 매뉴얼 기반 안내 페이지와 공식 갤러리·날짜코드 완보자 사진방입니다. 운영에는 아래 4단계 SQL과 사진방 서버 환경변수 설정이 추가로 필요합니다. 환경변수가 없는 개발 환경은 저장 없는 보고용 미리보기로 동작합니다.

## 운영 중 프로젝트의 추가 변경

4단계까지 완료한 프로젝트는 `supabase/05-public-gallery-view-only.sql`만 추가 적용합니다. 공식 갤러리는 열람만 제공하며 공개 원본 파일 접근을 차단합니다. 날짜코드 완보자 사진방만 다운로드를 제공합니다. 기존 신청별 동의 사본은 유지합니다.

3일 전 환불 마감, 사진 선택 동의, 관리자 엑셀 가져오기는 `supabase/03-consent-import.sql`을 추가 실행해야 합니다. 새 프로젝트는 초기 SQL 뒤에 03, 04를 순서대로 실행합니다. 운영 중인 프로젝트는 초기 SQL을 다시 실행하지 않습니다. 이어서 `supabase/04-public-gallery.sql`을 적용하면 두 갤러리와 최신 동의·환불 문구를 사용할 수 있습니다. 최신 코드는 4단계 SQL 적용 전 실제 신청을 차단합니다. SQL은 기존 정책 문구를 새 기준으로 갱신하고 기존 신청별 동의 사본은 보존합니다. 관리자 미리보기·확정 절차는 [가져오기 설명서](docs/기존신청자-가져오기.md)를 참고하세요.

공식 공개 갤러리와 완보자 사진방 운영 방법은 [갤러리 설명서](docs/공개-사진갤러리.md)를 참고하세요. 이미 03까지 적용했다면 새로 04만 실행합니다. 기존 참가자와 동의 사본은 보존합니다. 완보자 사진방은 서버 전용 `SUPABASE_SECRET_KEY`를 Vercel Production의 Secret 변수로 추가하고 Redeploy해야 합니다. 이 키는 공개 변수에 넣지 않습니다.

## 개발

Node.js 24에서 검증했습니다. 기존 `/workspace/SafeRoad` 체크아웃을 사용합니다.

```sh
cd /workspace/SafeRoad
npm ci --cache /workspace/.npm-cache
npm test
npm run build
npm run dev
```

`npm test`는 입력 검증과 PGlite의 실제 PostgreSQL 엔진에서 SQL 스키마, 권한, 회차 변경·취소·환불을 검증합니다. Supabase Auth/REST 서비스 자체를 대신 검증하지는 않습니다.

## Supabase 연결

1. 본인 계정으로 Supabase 프로젝트를 만듭니다.
2. 새 프로젝트의 SQL Editor에서 `supabase/schema.sql`을 **한 번만** 실행합니다. 기존 운영 데이터가 있는 프로젝트에서는 실행하지 않습니다. 전체 복사가 어려우면 대신 `supabase/01-tables.sql` → `supabase/02-functions.sql` 순서로 각각 한 번 실행합니다. 두 단계 방식과 전체 스크립트 방식을 섞어 실행하지 않습니다. 1단계만 완료한 상태에서는 접근을 차단해 두며 신청 기능은 아직 없습니다.
3. Authentication → Users에서 관리자 이메일·비밀번호 계정을 만듭니다. 참가자에게 회원가입은 제공하지 않습니다. 사용하지 않는 공개 신규 가입은 Auth 설정에서 비활성화합니다.
4. 생성된 관리자 User UID를 이용해 SQL Editor에서 아래 SQL을 실행합니다. UID는 비밀번호가 아닙니다. 아래 예시 문자열을 실제 UID로 바꿉니다.

```sql
insert into private.admins(user_id) values ('관리자-User-UID');
```

5. `.env.example`을 참고하여 `.env.local`에 Project URL과 공개 anon key를 설정합니다.

```text
NEXT_PUBLIC_SUPABASE_URL=프로젝트-URL
NEXT_PUBLIC_SUPABASE_ANON_KEY=프로젝트-공개-anon-key
```

공개 anon key는 브라우저 사용을 전제로 한 키입니다. **service_role / secret key를 여기에 넣지 않습니다.** 데이터 보호는 관리자 권한과 RLS로 적용합니다. 비밀번호·비밀키는 GitHub나 채팅에 올리지 않습니다.

6. 개발 서버를 다시 시작하고 `/admin`에서 로그인합니다.
7. 정책 설정에서 최종 개인정보 안내와 환불 기준을 저장하고 공개 승인을 선택합니다. 회차별 시간·코스·안내일을 확인하고 접수를 엽니다.
8. 가상 정보로 신청 → 입금 확인 → 날짜 변경 → 회차 취소 → 연락 확인 → 환불 완료를 검증한 후 실제 접수합니다. 테스트 신청은 운영 프로젝트와 분리하는 것을 권합니다.

## GitHub와 Vercel

GitHub main에 연결된 Vercel 배포를 사용합니다. 아래는 새 환경에서 처음 연결할 때의 절차입니다.

1. 이 코드와 lockfile을 GitHub `ptkrlee/SafeRoad`에 저장합니다. 기존 저장소는 최초 확인 당시 커밋이 없는 상태였습니다. 기존 파일·원격 상태를 다시 확인하고 저장해야 합니다.
2. Vercel에서 해당 저장소를 Import합니다. Framework는 Next.js, 프로젝트 루트는 이 `package.json`이 있는 디렉터리, Node.js는 24를 선택합니다.
3. 위 두 환경변수를 설정합니다. 테스트 배포는 테스트용 Supabase에, 실제 배포는 운영용 Supabase에 연결하여 Preview가 실제 신청정보에 접근하지 않도록 합니다.
4. 배포 후 실제 주소에서 관리자 권한과 신청·완료·접수 마감 동작을 다시 확인합니다. 비로그인/비관리자가 신청자 명단을 조회할 수 없는지도 확인합니다.
5. 도메인·문자 서비스는 별도 연결합니다. 현재 버전은 자동 문자를 보내지 않습니다.

## 포함된 기능

- 회원가입·본인인증 없는 직접 신청. 신청번호는 조회용 인증수단이 아닙니다.
- 한국시간 기준 세 회차, 인원·입금자명·필수 동의 검증, 동의문 버전 보관.
- 완료 화면: 참가비 합계, 입금처, 예금주, 문자 안내 예정일, 취소·문의 번호.
- 관리자 로그인 및 DB 관리자 명부 기반 권한 제한.
- 회차별 접수 개방/마감, 정원·시작 시간·코스·안내 예정일 설정.
- 통합 명단, 현재 회차 필터, 변경자 표시, 최초 회차 보존.
- 수동 입금 확인·취소·환불 완료·연락 확인 기록.
- 회차 취소 시 변경 유입 신청자를 포함한 전체 현재 참여 예정자 취소, 안내 필요 재설정, 입금 확인자 환불 대기 전환.
- 관리자 작업 이력과 날짜 변경 전후 상태 기록. 운영 테이블은 클라이언트의 직접 수정을 허용하지 않습니다.

## 아직 연결·확정하지 않은 항목

- **자동 문자·발송 결과:** 없음. 예정일은 화면 표시용이며 예약 발송이 아닙니다. 직접 연락한 뒤 관리자 상태를 기록합니다.
- **은행·실제 환불:** 연동하지 않습니다. 관리자가 뱅킹 업무 후 기록합니다.
- **미입금·최소인원 미달 자동 취소:** 없음. 관리자가 확인·취소하며 관련 정책을 자동처리인 것처럼 안내하지 않아야 합니다.
- **엑셀 내려받기, 참석·미참석 처리 화면, 회차 추가 화면:** 후속 개발 범위입니다. 엑셀 가져오기는 추가 SQL 설치 후 관리자 전용 기능으로 제공합니다. 초기 3회차와 현재 회차 이동·취소·정산 업무를 구현했습니다.
- **실제 Supabase/Vercel 연동·실제 기기 확인:** 계정 연결 후 검증이 필요합니다. SQL 테스트만으로 운영 배포 완료를 의미하지 않습니다.
- **대량 운영:** 명단은 최신 1,000건, 로그는 최신 50건입니다. 화면에 한도 안내를 표시합니다. 규모 확대 시 페이지 나누기·검색·내보내기를 구현해야 합니다.
- **개인정보 보유·삭제·백업:** 동의문과 실제 삭제 일정을 확정하고 Supabase 요금제의 백업·복원 기능을 확인해야 합니다. 자동 삭제 작업은 아직 없습니다. 공개 URL에 무인 접수를 열기 전 스팸·접수 남용 방어도 운영 규모에 맞게 추가합니다.

상세 운영 기준과 초기 확정 사항은 [관리자 설명서](docs/관리자-설명서.md)를 참고하세요.
